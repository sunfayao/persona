# Internationalization (i18n)

The web app and the hub share this policy. Implementations differ, but the language list, fallback rules, terminology and protocol agree. This document takes precedence in a conflict. How to add a string is in `AGENTS/08-text-and-languages.md`.

Code comments, documentation and commit messages are English. User-visible strings belong in localization resources, with `en`, `zh-Hans` and `ja` supported consistently. Additional languages are added through resources, not hardcoded UI branches.

These three languages ship. The web app uses their canonical codes in settings, resource names and requests to the hub, without regional suffixes. Web and hub discover supported languages from resources; see "Adding a language" below.

## Choosing a language

The "Language" setting (web: **Settings › General › Appearance › Language**) has four options: **Match system** (default), 简体中文, English and 日本語.
An explicit selection wins. When matching the system, resolve only the system's **first preferred language** (do not look for a second match):

| First preferred system language | Result |
| --- | --- |
| Any Chinese variant: `zh`, `zh-Hans`, `zh-CN`, `zh-SG`, `zh-Hant`, `zh-TW`, `zh-HK`, `zh-MO`… | `zh-Hans` |
| Any Japanese variant: `ja`, `ja-JP`… | `ja` |
| Unsupported languages (currently including `fr`, `ko`, `de`), English, or unavailable preference | `en` |


Match the language subtag (the first segment, case-insensitive, treating `_` as `-`), so Traditional Chinese also resolves to Simplified Chinese. The web app implements and unit-tests this resolver; it does not rely on the browser's own matching.

- When a translation is missing in the target language, fall back to `en`, then `zh-Hans`, then display the key (tests catch this).
- Language changes take effect immediately, without a reload.
- Never translate "Persona" or user-defined avatar names.

## Dates, numbers, and sorting

Use the platform formatting APIs (`Intl.*`). Do not assemble date labels such as 「月」「日」「周」 (month, day, week) by hand, or hardcode `zh_CN`.
Formatting locale: use the browser's locale when its language matches the current UI language (preserving regional conventions, such as date order in `en-GB`); otherwise use the UI language code (`zh-Hans`, `en` or `ja`).
Use `Intl.RelativeTimeFormat` for relative time (「3 分钟前」, "3 minutes ago"). Use plural rules (English distinguishes one / other; Chinese and Japanese have only other).

## Copy style

- **Chinese**: spaces between Chinese and English or numbers; use 「」 for quotation marks.
- **English**: conversational and concise, sentence case. Do not translate Chinese word for word: use Unread for 「完成未看」 (completed but unseen), not Completed not viewed. Buttons use verbs (Approve, Send); an empty state explains the next step in one sentence.
- **Japanese**: use the polite です・ます style for sentences, and noun phrases for buttons and labels (「承認」「送信」「設定を開く」: approve, send, open settings). Use full-width punctuation 「、」「。」 and 「」 for quotation marks.
  **Do not insert spaces** between Japanese and English or numbers. Retain long-vowel marks in katakana (コンピューター、サーバー: computer, server).
- All three languages must fit. English is on average 1.5–2 times longer than Chinese; Japanese is slightly longer than Chinese. A button label stays on one line in all three: shorten the copy or use an icon; do not wrap or truncate it.
- Always name placeholders (`{count}`, `{name}`), allowing each language to set its own word order. Do not concatenate fragments (`"已发送给" + name`, "Sent to " + name, must become a complete sentence with a placeholder).
- A placeholder may carry a whole sentence (an error or reason from the hub or a node, ending in `。` or `.`). When the text puts its own punctuation right after the placeholder (`（{reason}），`, `{error}。`; any of `）` `，` `。` `：` `；` `、` and their ASCII forms), the web's `interpolate` and the hub's `fill` drop the value's final full stop, so the text never reads `。），` or `。。` (an ellipsis keeps its dots).

## Platform mechanisms

| Part | Catalog location | Mechanism |
| --- | --- | --- |
| Web | `web/src/i18n/locales/<language>/<namespace>.json` | A small in-house `t()` (`web/src/i18n/index.ts`). `_meta.json` declares each language's native name and matching subtags; the shared Vite plugin `web/i18n-catalogs.ts` generates a separate module per language from JSON. The catalog comes in two parts: what the first screen reads, listed in `web/src/i18n/startup-namespaces.json` as whole namespaces or single keys (the build fails, naming the key to add, when first-screen code reads another), and the rest, which loads after the first screen. Keys are `namespace.name`, placeholders are `{name}`, and plurals use `_one` / `_other` suffixes (`Intl.PluralRules`). `tRich()` (`rich.tsx`) renders complete sentences containing elements. Dates, numbers and lists go through `formatDate` / `formatNumber` / `formatRelative` / `formatList` (`Intl`). The admin UI's `admin-*` namespaces are separate and loaded only by the admin UI |
| hub | `server/internal/i18n/locales/<language>/<namespace>.json` | `_meta.json` declares each language's native name and matching subtags. `i18n.T(lang, key, args)` uses the same format as the web app; catalogs are embedded in the binary with `embed`, and each language is parsed the first time a text needs it (`T` falls back to en, then zh-Hans, only for a missing key). User-visible text (push notifications, task notifications, injected messages, status and error copy, server-rendered web pages) uses the user's language. Command-line output uses the terminal's language ("Command line" below). Logs are not localized |
| Prompts | `server/internal/prompts/` | A single English prompt source, not a copy per language (`AGENTS/05-prompts-and-agent-tools.md`). Places that ask for a reply in a particular language use a template variable whose value is the language's native name, such as 简体中文, English or 日本語 |

On the hub: use `i18n.T(lang, key, args)`. Synchronous request errors use `i18n.Err(key, args)`; `apierr` writes `error` in the request's language (`Error()` remains Chinese, keeping log text unchanged). Asynchronous notifications use `notifyWSFrom`, producing a version for each connection's language.

Both sides check every declared language for matching keys and placeholders and prevent new hardcoded interface text (excluding tests and comments):

| Part | Checks | Hardcoded-Chinese baseline | How to run |
| --- | --- | --- | --- |
| Web | `web/src/i18n/catalog.test.ts`: matching metadata, namespaces, keys and placeholders across all languages; `_one` has `_other`; "Persona" is untranslated. Keys in `t("…")` / `tRich("…")` exist, with all placeholders supplied. Every key is used: the code spells it out (or its plural base), or builds it from a spelled-out prefix | `web/src/i18n/hardcoded-baseline.json` (per file; may only decrease) | `cd web && npx vitest run src/i18n` |
| hub | `server/internal/i18n/i18n_test.go`, `hardcoded_test.go` (below) | `server/internal/i18n/hardcoded-baseline.json` (per file; may only decrease) | `go test ./internal/i18n/` (in `server/`) |

For Chinese that must remain to match literal source text, such as hub output or a model prompt, add an `i18n-ignore` comment on that line or the preceding line (`// i18n-ignore: <reason>`).
Hub checks live in `server/internal/i18n/i18n_test.go`: `TestCatalogsAgree` validates every discovered catalog; `TestCallSitesUseKnownKeys` scans non-test code under `server/`.
Literal keys passed to `i18n.T` / `i18n.Err` must exist in the catalogs. When passing a literal `i18n.Args{...}`, supply every placeholder (keys with only plural forms also need `count`). Dynamically assembled keys and non-literal arguments are not checked.
`TestEveryKeyIsUsed` is the other direction: every hub catalog key must be reached from that code, so a key is removed together with its last caller. It counts a literal equal to the key or its plural base, the constant left side of a `+` concatenation or of a `fmt.Sprintf` format, literals passed to a wrapper that calls `i18n.T(l, "prefix."+name)`, and the prefixes accepted by this package's catalog template filters (`DeploymentText` and friends).
`TestHardcodedChineseBaseline` (`hardcoded_test.go`) scans packages that can send text to clients (`hardcodedDirs`) and counts string literals containing Chinese or Japanese per file, decoding escapes first. Counts may only decrease from `hardcoded-baseline.json`; new files or increases fail. The scan is conservative: not every remaining string reaches a client, so check a string's destination before migrating it, rather than translating logs or prompts to lower the count. Excluded: command-line code (`cmd/`, `link/`, `*cli.go`), node and `transcript/` (the hub rewrites their original text), prompts, and files listed in `hardcodedSkip` with reasons.
`TestHardcodedTerminalBaseline` is the same ratchet for the command lines (`terminalSources`), recorded in `hardcoded-terminal-baseline.json`: what they print moves into the catalogs ("Command line" below), so these files may only lose Chinese too.

## Command line

What a command prints for people (`personad`, `persona-hub`, `persona-node`, `persona-manager`, `persona-link`) is in the **terminal's language**, not the user language: a hub is often set up or repaired over SSH from a machine in another language.
`i18n.Terminal()` reads `PERSONA_LANG` (a catalog code or BCP 47 tag, for when the locale cannot be changed), then the POSIX locale's messages category in its own order (`LC_ALL`, `LC_MESSAGES`, `LANG`): the first one set wins, its language part is resolved as above (`zh_TW.Big5` is zh-Hans), and `C`, `POSIX`, an unknown language or nothing set is English.
A command that calls the running hub sends that language as `Accept-Language`, so the hub's own text (errors, permission lines, statuses) comes back in it; a command that has to recognize a hub error checks its `code`, never its text.
Machine-readable output (JSON such as `extension show`, `--get` values, `RESULT` lines) is not translated. Catalog namespaces are per command family (`extmgr-cli`, `hub-cli`, `hub-doctor`, `hub-setup`, `link-cli`, `link-errors`, `link-peer`, `link-service`, `manager-cli`, `node-cli`, `node-doctor`, `scriptcli-ask`, `scriptcli-notify`); tests pin the language with `PERSONA_LANG` rather than relying on the machine's locale. Logs are English rather than terminal-localized.
Persona Link keeps the canonical error text in `persona-link run` status, `status --json`, saved status, SSH JSON and peer messages; only its separate human renderer selects a translation. Passive peer messages keep their canonical Chinese, and candidate failures keep the full-width-semicolon delimiter. A foreground `run` error uses the terminal language, while early stderr redirected by a service is English.
A report that a command prints and a page also shows is built once as data and worded where it is shown: `hub doctor` collects items (`ok` / `problem` / `info`, an item, its detail) and next steps, the command prints them in the terminal's language and the admin page's **Run checks** (`POST /api/v1/admin/doctor`) gets the same items in the page's language. A command's printed text is never parsed back into data.
`hub setup` speaks the installer's language when it has one (`--lang`, else `PERSONA_INSTALL_LANG`, which `install.sh` sets from the language it ran in), else the terminal's; its `--json` lines word `detail` and `next` the same way and keep `step` and `ok` as machine fields.
`node doctor` words the same ordered report in the terminal's language. Its `--json` always emits the original zh-Hans human fields byte for byte, whatever the terminal's language. The preflight child keeps its C-locale tab-separated protocol; wording is chosen by the parent that builds the displayed check.
`node.doctor` and the local `{"kind":"preflight"}` request accept an optional `locale`. Without it they return the original zh-Hans report. A hub forwards only an explicit `Accept-Language` from the machine-page request; a header-less request keeps the zh-Hans report. A node that does not know the field ignores it and its Chinese report passes through unchanged.
The manager's join sends `Accept-Language` too. `manager capabilities --json`, service files, protocol codes and raw remote errors stay machine data.
`cmd/password-wasm` is a browser JSON protocol, not a terminal command. Its error strings stay byte-identical with `i18n-ignore` protocol annotations; terminal locale and hub catalogs do not belong in the browser cryptographic client.

## Adding a language

Web and hub discover supported languages from resources. To add Korean (`ko`), for example, add translations without changing a switch, enum, settings page or checker:

- **Web**: copy the English directory under `web/src/i18n/locales/` to a new `ko/` directory, translate its namespace JSON files, and set `_meta.json` to `{"name":"한국어","matches":["ko"]}`. Translate the separate `admin-*` namespaces too. The shared Vite plugin generates the client and admin modules; the picker and preload script discover them automatically.
- **Hub**: copy the English directory under `server/internal/i18n/locales/` to `ko/`, translate the JSON files, and add the same `_meta.json`. The directory is embedded in the binary. `Langs`, `Resolve`, `Valid` and the language name supplied to prompts update automatically. Cardinal plural categories use the `golang.org/x/text` CLDR rules.

Run the web catalog and preload tests and `go test ./internal/i18n` after adding resources, then build and inspect the pages. The checks automatically cover new languages and reject missing keys, placeholders or metadata. Web and hub look up a missing entry in English, then Chinese, using each fallback language's own plural rules; fallback does not mean a translation is complete.

The protocol fields are unchanged. A new language uses its own BCP 47 code. A hub that does not recognize it keeps its existing fallback; clients that omit locale keep the default behavior. Ship web and hub resources together.

## Deployment errors across requests

Deployment jobs keep canonical source-language errors in Postgres and manager reports, so a language change does not freeze the job in its starting language. `i18n.DeploymentText` matches only the deployment catalog templates (including known node capability reasons), then formats them for the current HTTP request or WebSocket connection. Machine snapshots, live machine events and resumed events translate copies; persisted records, RPC retry codes, versions and unknown node/SSH details stay unchanged. Changing `client_hello.locale` refreshes the full client's current machine status immediately.

Unknown-machine HTTP errors and the machine settings validation errors use `i18n.Err` and the request's `Accept-Language`. Undeclared routes use the router's standard response and are not localized.

## Protocol: telling hub the language

Hub needs two language choices: the language of **this request / connection** (synchronous errors and status copy), and the language of **this user** (asynchronous output: push notifications, assistant replies, injected messages, bot replies).
The web app sends only the resolved code (`zh-Hans` / `en` / `ja`), not "Match system". When the user changes the language, or the system language changes while matching the system, it resends it in both places below.

| Where | Field | Purpose |
| --- | --- | --- |
| Every HTTP request | Header `Accept-Language: <code>` | User-visible text in this response (`error`, status explanations, server-rendered web pages). The browser's own `Accept-Language` (`en-US,en;q=0.9`) is also accepted; the first entry is resolved with the fallback rules above |
| WebSocket | `client_hello.locale` | Copy such as `notify` and `error` on this connection; also updates the user language (below). Browser WebSockets cannot carry custom request headers, so this field is required |

The web app sends both (`web/src/lib/api.ts`, `lib/store.ts`).

For each hub broadcast, machine status and extension events are localized once per receiving language, and connections using that language share the resulting bytes. The cache lasts only for that broadcast and its event type. For events retained in the resume log, the hub keeps the canonical payload with its sequence number; resumed events are localized for the reconnecting client.

**User language**: hub stores it in Postgres `settings` (`user_locale`). Assistant replies, injected messages, task notifications, Lark / WeChat bot replies and push notifications all use it. If no client has ever reported a language, it is hub.json's `initial_locale`: the language the installer ran in, written by `personad hub setup` ([config.md](../operations/config.md)). It is not saved as `user_locale`, so the first device to report a language still sets it. A hub without `initial_locale` (one set up by hand or in Docker) uses `zh-Hans`.
It changes only when **a device's own interface language changes**. The hub remembers the `locale` each device last reported in `client_hello` (`hub.device_locales`, the 64 most recently changed devices) and counts only clients with the `full` role (link and linked-hub credentials do not count):

- The first device to report a language sets the user language when none is saved yet.
- A device reporting a different language than it did before (the user picked another language, or the system language changed under "Match system") sets the user language to the new one, whether on a new connection or by sending `client_hello` again on the same one.
- A device reporting for the first time, or reporting the same language again, is only remembered. Another device connecting in its own language leaves the user language alone.

A device is its device credential; a connection on the main token is identified by its hello's `device_id`, and one with neither can only set the first language.

The hub includes `locale` in `hello.features`, and also a `locale` field in `hello` (the current user language).
The `locale` in extension UI context keeps its region-bearing BCP 47 format, such as `zh-Hans-CN` ([AGENTS/06-wire-contracts-and-extensions.md](../../AGENTS/06-wire-contracts-and-extensions.md)). The web app sends the browser's `navigator.language`.
[protocol.md](protocol.md) is authoritative for field details.

MCP descriptions and schema guidance use the owner's locale at manager discovery and connector catalogs. New generated arguments follow that locale; quoted source text and title-kind enums remain unchanged. Updating the manager profile invalidates discovery cursors so connected models can refresh their descriptions. This does not rewrite existing task criteria, messages or extension-authored declarations.

## Text that stays in one language

- **Extension contribution titles**: an extension's name, description, settings form and secrets come in the request's language from the package's `l10n/<language>.json` and the index entry's `l10n`, picked by the hub. Contribution titles (pages, navigation entries, shortcuts) and built-in extensions have one language.
- **Refusal notices** (`Item.model_refusal`): the hub adds a localized explanation and recovery guidance in every supported language, while preserving Claude Code's original model names, category, scope, explanation and raw record. Unknown refusal subtypes receive a neutral heading.
- **Chinese written by the node in chats** (`server/internal/transcript`): the node does not know the user language. Before sending items or sessions to the web app, the hub rewrites recognized text according to the connection or request language (`hub/transcript_text.go`: task notification titles are rewritten by `task` kind and status; `已中断` (interrupted), `/loop 到点` (/loop due), Codex events, agent teams labels, `activity`, a workflow agent's `latest_tool.summary`, a subagent's `last_tool.summary`, commands moved to the background on timeout, and `来自` (from) in queued messages are recognized from the node's literal output). The runtime bridges under `integrations/` write their own words the same way and the hub recognizes them too (`transcript.Runtime*`): an error's notice and a runtime row's `last_text` for an agent that stopped on one (`出错了：…`, error: …), a failed command's `（退出码 N）` (exit code) after its output, and `（已取消）` (cancelled) as a cancelled call's result. Still Chinese: `上下文已压缩` (context compacted), `已从压缩的上下文继续` (resumed from compacted context), `压缩上下文` (compact context) (the web app uses these to recognize compaction dividers and /compact echoes), `API 错误：…（正在重试 / 重试 N 次后放弃）` (API error: …; retrying / giving up after N retries, parsed by the API error card), and `…（已截断…）` (…truncated…, recognized to show "View full text"). Translating these needs structured fields on items, rendering from those fields, and then the hub replacing the text. Items read by the assistant and channels are not rewritten (`assistant/done.go` tests for `已中断`), so these lines forwarded by Lark / WeChat bots also remain Chinese.
- The "type" in assistant chat titles (`功能` / `修复`, feature / fix…) consists of fixed Chinese terms parsed by the assistant. The topic follows the user language; the type remains Chinese.
- **Hub text the web app parses as literal Chinese**: the model configuration status `未验证` (unverified), session titles `MMDD | 类型 | 主题` (type | topic) and `旧主对话 · 至 M月D日` (old main chat · through month M, day D), and legacy injected messages themselves (the web app displays the hub's localized `injected.line`). Localized Agent wakes use a structured marker; old Chinese wakes keep their parser.
- Text written into chats or sent to an Agent or model varies by implementation; new prompts follow `AGENTS/05-prompts-and-agent-tools.md`. Web slash commands (`/继续`, /continue, etc.) and `用户拒绝了` (the user denied it) are sent in the UI language; the first line of a task reference, `任务「…」` (task "…"), `（整篇）` (entire document) inside `<persona-context>`, and instructions to stop `/loop` remain Chinese because they are read back or matched.
- Persisted text (run history, Inbox sorting reasons, default device-token names, audit records) keeps the language used when written; it is not rewritten on a language change.
- The WeChat extension gets its language from `initialize`'s `hub.locale` at startup. A language change does not take effect until its next restart.
