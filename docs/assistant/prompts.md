# Prompts

Every prompt personad writes for a model lives in `server/internal/prompts/`: one file per prompt, using Go `text/template` syntax, embedded in the binary with `//go:embed`.
Callers only prepare data (machine lists, how to address the owner, collected context, and so on) and call this package's typed render functions to get text. Go code no longer builds prompts with `fmt` / `+`.
`prompts` does not depend on `hub`, `kb`, or `node`. Data structures are defined in `prompts`; callers convert their own types.

What counts as a prompt: system / user text sent to a model, CLAUDE.md written to the assistant directory, snapshots at the start of each message, the first message sent into a chat,
and explanatory text that wraps data in a prompt (`<persona-context>` blocks, lines such as "类型：飞书私聊"—"Type: Lark direct message"). The user's own words, collected chat history, and document bodies are **data**, not template content.
MCP tool descriptions and parameter explanations shown to models are also prompts, in `mcp/` (see "MCP tools" below). Tool-result text returned to models still lives in the respective code.

## Language

Every prompt is written in English, and only in English: templates carry no language branches. What the model writes
for the owner still follows the owner's language. A prompt that asks for owner-facing text (a title, a summary, a
reason, a report) says so with the `lang` template function, which prints the English name of the owner's language:
`in {{lang .Language}}` (`{{lang .Lang}}` in MCP tool descriptions). Callers pass the language as they have it, a
native name (`answerLanguage(hello.Locale)`: `English`, `日本語`, empty for Simplified Chinese) or an i18n code;
`prompts.AnswerLanguage` maps all of them. Source quotations, identifiers, recorded decisions and the owner's words
remain data: a prompt never asks for them to be translated.

The assistant's instructions say once that tool arguments the owner reads (titles, reasons, criteria, messages) are
written in the owner's language; tool descriptions do not repeat it.

Text that code recognises keeps recognising what older versions wrote. The injected messages
(`injected.go` `ParseInjected`, `web/src/lib/injected.ts`), the relay header (`message_source.go`,
`web/src/lib/message-source.ts`), the delivery line (`assistant/delivery.go`), the peer message heads
(`peer_message.go`) and the default routines (`routine_*_former*.md`) each hold the Chinese shape they had before the
prompts became English-only, beside the current one: transcripts and stored rows keep the old text. Language-independent
markers (`<persona-wake>`, `<persona-limit-continue />`, `<persona-inbox>`, `<persona-answer-again />`) are unchanged.

Strings shown to the owner (display lines such as `proto.Injected.Line`, notifications, card text) are not prompts:
they go through the localization resources (`docs/protocol/i18n.md`).

## MCP tools

When adding, renaming, removing or changing a work-management tool, check the affected workflow in the built-in
`persona-work` skill (`server/internal/assistantskills/builtin/persona-work/`) in the same PR. Put operation-specific
changes in the relevant reference. Check that the catalog and startup hint still route a natural request to it. Keep the
catalog description short and retain the contracts that task Agents use. A scheduled round with a start grant gets
its planning steps inline and keeps `task_plan` available on its first call when the guide is enabled.
Keep the exact built-in names taught by the skill in `server/internal/assistant/tool_loading.go`. With the Lab on,
`work_tools_search` advertises selected definitions to that MCP connection using `notifications/tools/list_changed`.
Each operation uses its original MCP tool and caller authorization. A granted scheduled round can use its existing safe preflight reads and then call `task_plan` directly.
Reading a skill or other outside content still requires the ordinary Start approval.

Each MCP tool hub provides to Agents / the assistant has one file: `mcp/<scenario>/<tool-name>.md`. The filename is the tool name. Contents: one paragraph of model-facing description, a blank line,
then a ```json code block containing the input schema (parameters and their descriptions). They are templates with `MCPData.Lang` (`en`, `ja`, or empty for the historical default). `Tool(name)` keeps the default; `Tool(name, lang)` renders the caller's language, with English fallback for other language codes. The schema is loaded with `json.Compact`, so layout is arbitrary and does not affect transmitted bytes. Literal recipe placeholders such as `{{since}}` must be escaped as template string literals, not evaluated as prompt actions.

Tool descriptions are English. A field whose value the owner reads names the owner's language with `{{lang .Lang}}`; the general rule for such arguments is stated once in the assistant's instructions, not in every description.

The manager applies the owner language from `hello.Locale` after discovery filtering, including ordinary Agents, assistant/supervision lists, work-machine restrictions, guest meeting rooms and restricted task-leader aliases. Runtime leader registration follows the same contract. A profile update invalidates discovery revisions. The extension manager and connector registry/catalog use context language; the assistant supplies the owner language when collecting their tools. Voice session starts use the conversation's existing language precedence. Built-in phone-queue tools join normal discovery; device-authored schemas remain source data. Static mail/connector constructors can still return default definitions: localization occurs at registry/catalog and final manager discovery boundaries.

`LocalizeTool` recognizes a built-in only when its name (or an explicit restricted alias), description and compact schema match a known built-in version. It never translates an arbitrary extension or phone declaration just because its name matches. Catalog localization copies shared slices. Empty language and `zh-Hans` retain every original description and compact schema byte, pinned for all 143 definitions against upstream `143ea314f` in `prompts/testdata/mcp_legacy.json`; language schemas differ only in description fields. Changes to a tool contract update its digest for both legacy locales. Exceptions include the optional preset and pin request on #13357's optional leader role on `agent_supervise`, and #13362's `task_plan` supervision wording, including its `supervisor` parameter: planning direction leads own their tasks, main owns its own tasks, and explicit transfers persist, so its equal empty-language and `zh-Hans` digests are deliberately updated. Every other definition remains pinned to the upstream bytes. Caller goldens cover the node's transmitted assistant/Agent lists and ordinary/bound/meeting voice lists, with an upstream session-start capture too.

Source-sensitive text remains literal: conversation title kinds are fixed enum values consumed by `assistant/titles.go`; iMessage attachment markers describe source output; snapshot labels identify existing text; voice delegation uses the exact `状态：`, `停止：` and `回答：` prefixes consumed by `voice/send.go`. English/Japanese voice instructions explain those prefixes without renaming them. A meeting delegation has its own definition and must not acquire the bound Agent's status/stop/answer commands. Tool names, parameter keys, enum values, constraints, routing and permission semantics are unchanged.

and node's `gateTools` passes them to the runtime through `runtime.sock` (`node/assistant_runtime.go`).

Tool **lists and order** remain in code (the two functions above look up `prompts.Tool(name)` by name), as do call handlers. To add a tool, add a file in the relevant directory,
add its name to the list, write its handler, and use `UPDATE_GOLDEN=1` to update the `mcp_tools/` / `mail_tools` goldens (a new tool adds its own file and a line in its list's index). `TestEveryMCPToolIsUsed` catches tool files with no provider. `TestMCPToolsTableListsEveryTool` keeps the table above in sync: every `mcp/<dir>/` needs a row that lists all of its tools.

For to-dos, shared assistant instructions cover routing and responsibility; parameter formats, defaults and operation rules live in each tool's description/schema. Keep rules needed by task Agents in the association tools themselves: those callers do not receive the assistant's shared instructions. When consolidating text, preserve schema constraints and inspect both the tool snapshots and every affected shared-instruction variant before updating the size baseline through its guarded updater.

`agent_start`, `agent_send` and `task_plan` each keep their own compact `wait_seconds` guidance: track conversations receive these tools but use `space_claude_md.md`, not the shared `assistant/claude_md.md`. Moving the common rules only into shared assistant instructions would leave those callers without them; any further consolidation must preserve the complete inline-observation contract in every tool.

## Template rules

- Template names are paths without `.md` (`inbox/triage`); one prompt references another with `{{template "shared/user_rules" .}}`.
  Compose an Agent's sections (body, optional sections, lists) with `{{if}}` / `{{range}}` / `{{template}}` inside the template, not string concatenation in Go.
- **The file's final newline does not count** (editors always add one). Leave a final blank line if the prompt itself must end in a newline. `TestFilesEndWithANewline` requires every file to end with a newline.
- Defaults belong in templates (`{{or .Owner "用户"}}`—"user", the default sentence when no requirements are given), not callers. Different prompts use different default forms of address ("用户" / "我" / "你"—"user" / "I" / "you"); preserve them exactly.
- Template functions (`prompts.go`): `attr` (XML attribute escaping), `ctx` (body inside `<persona-context>` / `<persona-context>` blocks; see next rule), `output` (Agent answer in a voice `<agent_output>` data block: removes opening and closing tags for that block, `AgentOutput`), `join`, `indent`, `blank` (whitespace only), `first` (first n slice elements).
  Data preparation such as truncation (`textfmt.Clip`, `textfmt.OneLine`) belongs in the caller; passed values are already ready to insert.
- **Always pass other people's text inside blocks through `ctx`** (#3754). Quotes, forwarded messages, Inbox bodies, knowledge summaries, snapshot sections, and memory indexes may come from others (or paraphrase their words). A closing tag in the body can end the block early, turning subsequent text into the user's own words. `ctx` (`ContextBody`) removes closing tags once, then replaces `<` in the resulting text with `&lt;`; matching is case-insensitive and allows whitespace on either side of the slash and before `>` (readers recognize only literal `</persona-context>` / `</persona-context>`; this is a superset).
- A template is parsed the first time it is rendered, together with the templates it includes (`missingkey=error`), so a process holds only the prompts it writes (#2475). A syntax error panics at that render;
  `Names()` parses every template, so the tests surface it first, and `TestEachTemplateParsesItsIncludes` checks that rendering any template on a fresh set parses everything it may include.
  Rendering errors (wrong field names) panic directly, never handing a partial prompt to a model. `TestEveryTemplateIsUsed` catches unused templates.
- To write literal `{{` in a prompt: `{{"{{"}}`.
- Where user-facing output instructions say "use Chinese", replace that with a `Language` field (the language's own name, `English`, `日本語`; callers use `assistant.answerLanguage(hello.Locale)`, passing empty for zh-Hans),
  and `{{if .Language}}用{{.Language}}{{else}}用中文{{end}}` in the template ("use [Language]", otherwise "use Chinese"). Empty remains byte-for-byte identical to the original, leaving existing goldens unchanged; en / ja have separate `*.en.golden` / `*.ja.golden`
  (`assistant/claude_md.md`, `inbox/triage.md`, `inbox/group.md`, `inbox/draft.md`, `tools/session_title.md`; `docs/protocol/i18n.md`).
- Voice prompts (all under `voice/` since #3501; `instructions.md`, `target.md`, `agent_message.md`, `status.md`, `folded.md` in #3502, `ask.md`, `needs_you.md`, `answered.md` in #3504, `progress.md`, `observed.md`, `failure.md` in #3503, `nudge.md` in #2297, `read_aloud.md` in #5004, `meeting.md` in #3862 phase 4, `transcribe_caption.md` and `transcribe_verbatim.md` in #3862) have three whole-language versions. `Lang` is an i18n code (`en`, `ja`, otherwise Chinese),
  with `{{if eq .Lang "en"}}…{{else if eq .Lang "ja"}}…{{else}}…{{end}}` in the template. Goldens are `voice/testdata/prompts/<name>.<branch>.<zh-Hans|en|ja>.golden`
  (`go test ./internal/voice -run Golden`, `UPDATE_GOLDEN=1` to update). The fast layer speaks to the user; writing in the user's language makes the model continue in that language.

## Change a prompt

1. Edit the file under `server/internal/prompts/`.
2. Run golden tests and check that the differences are intended: `cd server && go test ./internal/hub ./internal/assistant ./internal/kb ./internal/node ./internal/voice -run Golden`.
3. After confirming, update goldens: `UPDATE_GOLDEN=1 go test ./internal/hub ./internal/assistant ./internal/kb ./internal/node ./internal/voice -run Golden`, and commit the `testdata/prompts/*.golden` diffs too.
   `TestGoldenAssistantContextMain` requires Postgres (runs only in `scripts/test/test-server.sh`). To update it, run on the hub machine with `UPDATE_GOLDEN=1`
   (`GOCMD='env UPDATE_GOLDEN=1 go test -count=1 -run TestGoldenAssistantContextMain' ./scripts/test/test-server.sh ./internal/hub`), then copy the two files back.
4. A judge's prompt (task done, delegation, triage): run its live check before and after the edit and put both tables in the PR ("Behaviour checks" below).

Note that `scheduleHeader` in `assistant/schedule.go` recognizes copied-back old headers by the first few lines of `assistant/task_run.md`: changing those lines requires updating it too.

## Add a prompt

1. Add `xxx.md` in the appropriate scenario subdirectory (or create a subdirectory if none fits, and add it to `//go:embed` in `prompts.go`).
2. Add a data structure and `RenderXxx` to that scenario's Go file; callers only fill the data. For an assistant prompt that file is a new `assistant_<topic>.go`, never `assistant.go`, whose names are frozen (`docs/server/architecture.md` "Registering a domain's entries").
3. Add a golden test in the caller's package (follow existing `*_golden_test.go` patterns: representative inputs, optional sections present / absent, empty / multi-item lists), and generate with `UPDATE_GOLDEN=1`.
   Use placeholder inputs only (`Example user`, `example.com`); `scripts/privacy_check.py` checks them.

## Golden tests

MCP tool goldens are in `hub/mcp_tools_golden_test.go` (the assistant's list, its variants with GitHub signed in and with iMessage handed over, and the regular Agents' list), `mail/mcp_golden_test.go` and, for a meeting's room, assistant/meeting_conversation_test.go (`meeting_room.tools`). They compare the transmitted `json.Marshal` content (goldens are indented for readability, with a one-to-one correspondence before and after indentation).

The hub's lists keep one golden per tool (#11252), so changing a tool's description or schema rewrites one small file and two PRs that change different tools never touch the same golden. Under `hub/testdata/prompts/mcp_tools/`, a list has `<list>.index.golden` (its tool names in order, one per line) and `<list>/<tool>.golden` (each tool as sent, indented); a variant has only `<variant>.diff.golden`, its difference from its base list: tools it leaves out, tools it offers changed in the same place, and tools it adds or moves, each new or changed tool in full. A run of added tools that ends the list is placed `at` the end, so a tool the base gains does not change the variant's difference. A tool both base lists offer (the mail tools) has a file in each, since the lists are built separately. `UPDATE_GOLDEN=1 go test ./internal/hub -run TestGoldenMCPTools` rewrites the index, the tool files and the differences, and deletes the files of tools a list no longer has (inside that list's directory only); without it the test fails on any difference, the order included, and on a stale file. Tests that read a whole list rebuild it with `mcptoolgolden.Load` (`internal/mcptoolgolden`), byte for byte what the list's single golden held before.

`hub/prompts_golden_test.go`, `assistant/prompts_golden_test.go`, and `node/prompts_golden_test.go` test at the caller layer (fake Lark gateway, fake model recording received
system / user text, knowledge base in a temporary directory), so they also cover data conversion. The clock in the snapshot's "Now" line is replaced with a placeholder before comparison.
On 2026-11-01, these goldens were generated from the original code before the move; after the move, identical inputs produced byte-for-byte identical output.
When assistant business logic moved to `server/internal/assistant` on 2026-11-04 (`docs/assistant/assistant.md`, "Boundary with hub"), its prompt goldens moved unchanged to `assistant/testdata/prompts/`, without regeneration. After assistant settings, main chat, and chat creation moved there the same day, `assistant_claude_md.*` and `main_handoff*` goldens also moved unchanged to `assistant/testdata/prompts/` (`assistant/claude_md_test.go`), byte-for-byte identical. When Inbox moved to the manager the same day, `inbox_triage.*`, `inbox_draft.*`, `inbox_judge*`, `inbox_agent.*`, and `inbox_group.*` goldens moved unchanged to `assistant/testdata/prompts/` (`assistant/inbox_golden_test.go`), without regeneration and byte-for-byte identical. When translation followed, `translate_*` moved there unchanged too (`assistant/inbox_translate_test.go`), also byte-for-byte identical.

A size ratchet watches the same goldens' weight (#6881, step P0 of `docs/design/proposals/assistant-instructions.md` 4a): `assistant/prompt_size_ratchet_test.go` measures the UTF-8 size of every `## ` section of the `assistant_claude_md.*` goldens (the part before the first heading counts as `#head`), of every tool object in the assistant's list (`hub/testdata/prompts/mcp_tools/`, rebuilt with `mcptoolgolden.Load`; the compact `json.Marshal` of the whole tool, description and input schema included, under the key `mcp_tools.assistant#<tool>`) of each `supervise.*` golden as a whole, and of the single `supervision_instructions.golden` fragment, and compares the numbers with the baseline `assistant/testdata/prompt_sizes.json`. Any piece growing past its baseline fails the test: growth is a decision made when the baseline is updated, never something a change slips in. The baseline's total only goes down: instructions grow one rule at a time, so a rule that has to grow is shortened or moved elsewhere first. A single piece may still grow when text moves between prompts and the total falls by more (a move into the shared instructions shrinks the goldens it came from); such a PR says where the text moved to. `PROMPT_SIZE_UPDATE=1 go test ./internal/assistant -run PromptSizeRatchet` rewrites the baseline after a shrink or such a move — it adds new keys and drops removed ones (a renamed heading shows up as a removal plus an addition) and refuses to write a larger total.

## Behaviour checks

Goldens pin the text a prompt renders to, not what a model decides on it. The judges that make one model call also have written-out cases with what the hub should end with, and a check that asks a real model about them (#2586):

| Judge | Prompts | The model call and the hub's rules after it | Purpose | Cases | Tests |
| --- | --- | --- | --- | --- | --- |
| Task done | `assistant/task_done.md`, `task_done_input.md` | `judgeTaskDoneWith` (`assistant/done.go`) | `inbox.judge` | `assistant/testdata/judge/task_done.json`: the verdicts that pass, plus the delivery state where it matters | `TestTaskDoneScenariosAreWellFormed`, `TestTaskDoneJudgeLive` |
| Delegation | `agents/delegate.md`, `delegate_input.md` | `judgeDelegateWith` (`assistant/delegate.go`) | `agent.delegate` | `assistant/testdata/judge/delegate.json`: answer or ask, the options that pass when it answers, and options the hub refuses on its own (red-line words) | `TestDelegateScenariosAreWellFormed`, `TestDelegateJudgeLive` |
| Triage | `agents/triage.md`, `triage_input.md` | `judgeTriageWith` (`assistant/agents_triage.go`) | `agent.triage` | `assistant/testdata/judge/triage.json`: done, unsure or blocked on the user / an agent / something external, plus the request, link or agent the card must carry | `TestTriageScenariosAreWellFormed`, `TestTriageJudgeLive` |

- Every case is synthetic and public: no real conversation, person, project or message.
- `Test…ScenariosAreWellFormed` runs with the other tests and needs no model. It checks that the cases are consistent with the hub: the values are ones the hub gives, and a model answering as a case expects leaves the hub with that result after its own rules (for example a done task held at a PR is undelivered, a red-line option is left to the user, a question the reply does not contain is dropped).
- `Test…JudgeLive` asks a real model and prints one row per case (expected × got). It runs only with `PERSONA_LIVE_AI='{"base_url":"…","api_key_file":"…","model":"…"}' go test -run 'TaskDoneJudgeLive|DelegateJudgeLive|TriageJudgeLive' -v ./internal/assistant`, never in CI. A case the model gets wrong fails.
- A case the hub is known to get wrong today carries `known` (why): the live check prints it as `KNOWN` and does not fail on it, so a run fails only on a regression. When a fix lands and the case passes, drop `known` in the same PR.

When you change one of these prompts, the hub's rules after the model, or the model behind the purpose, run that judge's live check before and after, and put both tables in the PR. A real case a judge got wrong goes in as a new synthetic case, rewritten so it names no real person, project or message.

Supervision events have behaviour cases of their own (#6879), since a supervising conversation is a whole conversation, not one judging call. `assistant/testdata/behaviour/supervision.json` lists synthetic cases, each naming a CLAUDE.md golden as the system prompt and a supervision event golden as the message; the model gets the assistant's tool list (rebuilt from `hub/testdata/prompts/mcp_tools/` with `mcptoolgolden.Load`, plus a Bash tool) and canned tool results, and the case checks the calls it makes: calls expected (optionally only after an evidence call such as `agent_read`), groups of which one must happen, and calls forbidden. Because the cases read the goldens, regenerating the goldens after a prompt change is what puts the new text under test.

- `TestSupervisionBehaviourCasesAreWellFormed` and `TestSupervisionBehaviourChecks` run with the other tests and need no model: every golden, tool and argument a case names exists, and the checks score sample calls as intended.
- `TestSupervisionBehaviourLive` runs each case `PERSONA_LIVE_RUNS` times (default 5) against `PERSONA_LIVE_AI` (Messages API only; `PERSONA_LIVE_CASE` runs one case; `PERSONA_LIVE_PARALLEL` bounds the concurrent runs, default 4) and prints passes per case. It calls the model directly, without Claude Code's own system prompt, the snapshot or earlier turns.

When you change `assistant/supervise.md`, the supervision rules in `assistant/claude_md.md` or a supervision tool's description, run it before and after and put both tables in the PR; a case that passes fewer runs afterwards blocks the change (`docs/design/proposals/assistant-instructions.md`, decision 1 of section 6).


The `todo_workspace` tool (`server/internal/prompts/mcp/todo/todo_workspace.md`) provides the explicit backend preparation and recovery actions documented in `docs/assistant/todos.md`, under "Backend workspace preparation". It shares the Manager service with HTTP clients; it does not start an Engine or replace legacy workspace tools.
