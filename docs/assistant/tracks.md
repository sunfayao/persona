# Tracks and spaces

A **track** is a named place the assistant's conversations run in, of a **kind**, with a directory of its own: its own chat directory, its own memory, its own instructions. Its conversations form a **space**, listed apart from the assistant's main chat. What is said in a space stays in it unless the user knows it leaves: what hides, redacts or confirms is decided by the track's information categories ("Information categories", "Using information by scene" below).

## Why spaces are separate

Some information is more private than work information, and longer-lived: it should stay useful once recorded, but should not show up in the context of work chats, nor be read by the main chat's tools or written into the knowledge base. Inside the main chat, memory, tools and the chat list are all shared and cannot be separated. With a separate directory, Claude Code's per-directory auto memory, CLAUDE.md and chat list separate naturally.

## How directories and memory are isolated

- **Directory**: a track's conversations run in the track's directory on the assistant's machine (`tracks/<slug>` in the state directory, default `~/.persona/tracks/<slug>`), alongside the assistant's own `<data dir>/assistant`. When the hub asks node to prepare the directory (`assistant.prepare`), the relative path it passes is the track's `DirName`. `identity.TrackDirOf`, `identity.SpaceOf` and `identity.SpaceAt` are in `server/internal/identity/paths.go`; `IsAssistantDir` also holds for a track's directory, so its chats, like assistant chats, are "assistant chats" (`assistant: true`) and use the same tools, authorization and questions.
- **CLAUDE.md**: a track has the baseline `server/internal/prompts/assistant/space_claude_md.md` followed by its `SPACE.md` ("Tracks and kinds"). Connector and plugin skills are installed the same way as in the assistant directory, but the instructions plugins give the assistant (`plugins.Instructions`) are not added: those were written for the main chat.
- **Memory**: Claude Code's auto memory is per working directory (`~/.claude/projects/<encoded dir>/memory/`). Only a track's chats read and write the track directory's memory; it is not in the main chat's context, and vice versa.
- **Files** (#3282): the main chat's Claude can read files on the computer with Read / Bash; separate directories do not mean unreadable. So the main chat (not a track's chat) starts with deny rules: Read and Edit may not touch the directories of the tracks the manager names on `assistant.prepare` (`deny_dirs`, capability `deny_dirs_v1`, #13177) nor their Claude project directories (memory, transcripts), `server/internal/node/trackdeny.go`; the CLI gets them via `--disallowedTools`. Deny rules override every allow: even after tapping **Always Allow in Session** or switching to bypass mode, the files cannot be read (tested on Claude Code 2.1.318). **Always Allow in Session** for file tools in the main chat also only allows the directory of that file (`hooks.go` `fileRuleScope`), instead of opening the whole tool. **Not blocked**: Bash can build the path in any number of ways (`cd .. && cat tr*`), so matching command text cannot catch all of them; blocking it fully needs Claude Code's sandbox or OS-level isolation. When the main chat runs on Codex, this rule does not exist yet either. The memory API with `?space=<slug>` reads and writes exactly this memory.
- **node**: node treats a track's transcripts as assistant chats, same as the assistant's. A track's chat is listed in its directory however its model `cd`s (into a subfolder, `/tmp`, anywhere), running and at rest (#2368): Claude Code writes the shell's directory after a `cd` into every transcript line, so the node goes by where the chat started (its start record, else the transcript's first `cwd`; `readQuickMetaSince`, `assistantHome`).
- **Which space**: a chat's space comes from the directory it started in; a `cd` into a subfolder or anywhere else does not move it. In the session list the hub sends, every chat of a track carries `space: "<slug>"` (`proto.Session.Space`, filled from cwd in `server/internal/assistant/fleet_sessions.go`, `server/internal/assistant/fleet_routes.go` and `server/internal/hub/assistant_link.go`); the assistant's own chats do not have this field. To decide which space a chat belongs to, the assistant looks at `space` first and falls back to the directory (`spaceOf` in `server/internal/assistant/space.go`). These classify, so they take the directory itself only (`identity.SpaceOf`, exact). What hides or confirms (below) also counts a directory inside a track (`identity.SpaceAt`, `identity.InSpace`): there, when in doubt, hiding is the safe side.
- **Registry and policy** (#13104): the manager's track registry (`server/internal/assistant/track_registry.go`) is the `assistant_tracks` table. A track has a kind (a domain space is one kind) and its directory is data: a new track defaults to `tracks/<slug>` whatever its kind. Kinds, templates and the versioned list of information categories are checked in code, not in the table. Conversations name their track in the wire field `space`. What hides, redacts or confirms never compares a track's name: it reads the track's `TrackPolicy` (lock screen and channels, extensions, knowledge-base writes, handing things out, the main chat's file tools). The main space has every switch off; another registered track's follow its default categories, and a slug the registry does not know has every switch on ("Using information by scene" below). The hub and the nodes cannot read the registry: a node learns the tracks' directories from the manager (`deny_dirs`) and tells sessions in them by `space`, and both treat any track as the strictest. Once noted in a track other than the main space, a conversation stays there (`assistant_conversation_spaces`).

## Information categories (#13246)

Collecting is not limited by track: every assistant conversation is tagged with the kinds of personal information it carries, so a later step can decide each use by the information's categories and the scene it goes to instead of by the track it came from.

- **Categories** (`server/internal/assistant/track_registry.go`, versioned in code, never user-defined): `health`, `finance`, `relationships`, `emotion`, `legal_id`. No category means general. Credentials are no category: they are filtered out before anything is kept.
- **A conversation's categories** (`conversationCategories` in `server/internal/assistant/info_tag.go`): its track's default categories, a floor nobody takes away, and what was tagged since, kept in the manager table `assistant_info_categories` by session id. They only grow: the model and agents only add, and only the user takes one away, which stays away (a `removed_by_user` row) until the user adds it back. When the categories cannot all be told (the store or the conversation's track cannot be read), uses outside the track are to take the conversation for sensitive.
- **Tagging after each turn**: once an assistant conversation's turn ended and stayed still, what the user said and the reply (the first 1,000 characters) go to the model use `info.tag`, a read-only use under Sorting (`inbox.triage`). Its prompt is `server/internal/prompts/assistant/info_tag.md`, in English whatever the owner's language, and the answer is category names only; the track's default categories are passed as the ones to look for especially. A track's conversations are tagged too: tagging is collecting, and limits belong to how information is used, so the first 1,000 characters of every such turn go to the model Sorting is set up with, which need not be the conversation's own. Answers are cached by text and model. A turn that cannot be read or tagged (no model set up, paused, timed out) leaves the categories as they were.

## Using information by scene (#13246)

What a piece of information may do is decided where it is used, by one function, `usage` (`server/internal/assistant/usage.go`), from what it is (its categories, whether they are all known, the track it came from) and where it goes. It never reads a track's name or kind: a track takes part only through its default categories, which everything from it carries.

| # | Scene | General | Sensitive (any category, or not known) |
| --- | --- | --- | --- |
| 1 | Inside its own track | Used | Used |
| 2 | The main chat or another track | By relevance | Only when on topic, never in a standing context; the main chat's Read and Edit are denied the track's directory |
| 3 | Handed to an agent or a computer | By relevance | Confirmed on the phone each time; a task plan does not start on its own |
| 4 | Lock screen and pushes | As usual | Only that there is news |
| 5 | Sent to other people | As usual | Confirmed on the phone each time |
| 6 | Read by an extension | As usual | Hidden unless the extension is the user's own or was granted every category |
| 7 | Written to the shared knowledge base | As usual | Refused |

Information whose categories are not known yet (not tagged, tagging failed or timed out) takes the sensitive side outside its own track. `TrackPolicy` sums these rules up as the switches the call sites read until each asks `usage` for its own scene (`policyOf`); a track's policy is that of its default categories, so a track with a sensitive default category keeps every switch on, the main space none, a slug the registry does not know every one, and only tracks with a sensitive default category have their directories denied the other conversations (`deny_dirs`). `TestUsageSensitiveTrackOutbound` maps every row of the table under "Outbound" to its scene.

Which categories a use reads depends on the scene:

- **A text leaving Persona** (scenes 3, 4, 5 and 7: a push or `notify_user`, `phone_notify`, `urgent_call`, a to-do reminder, a scheduled task's failure notice, a decision's push, "all cards" and "all questions" on Lark and the plugin channels, `agent_send`, `agent_start`, `agent_switch`, an A2A message or task from an assistant conversation, a task plan, `kb_update`) carries the categories tagged of its own words, within 800 ms, and its track's default categories (`exitPolicy` in `server/internal/assistant/info_use.go`). Never its conversation's accumulated ones: the main chat would soon carry every category and have everything confirmed. A track sensitive by default asks no model. When the words cannot be tagged in time (a timeout, a paused model, an error), the conversation's categories stand in when it was tagged and no turn of it waits to be tagged; otherwise the text is taken for sensitive. With no model set up for `info.tag`, a text carries its track's default categories, as before tagging.
- **A conversation as a whole** (scenes 6 and 2: an extension listing or reading it, a recall elsewhere) carries its accumulated categories (`conversationPolicy`); while a turn of it waits to be tagged they are not known. An extension reading the assistant's conversations (`assistant.conversations`, `assistant.messages`) is shown each by its categories; its other reads in the manager (the feed, card history, archived agents, memory) go by the track's default categories and its grant. To-dos, and every control (starting a conversation in a track, taking a run onto a to-do), keep the track's rule whatever the extension's trust or grants: trust widens reads only. The hub still hides every track from extensions on its own routes (session lists, transcripts, cards) for now.
- **Extension trust and grants** (scene 6, `server/internal/assistant/extension_trust.go`): an extension the user marked as their own (`trust: owner`, such as their memory extension) reads everything; any other is a third party's and reads sensitive information only of the categories the user granted it, each one (`assistant_extension_trust`, `assistant_extension_grants`). The extension manager names the reading extension (`assistant.extension_read`); a read that names none is a third party's with no grant. When an extension is removed, its trust and grants go with it (`assistant.extension_trust_forget`): installed again it starts as a third party's. With no grants given, every extension sees what it saw before, except that conversations of a track with no sensitive default category, and their memory, are no longer kept from it, and a main conversation tagged with a sensitive category is.
- **Only the user changes it** (`GET /api/v1/assistant/extension-trust`, `PUT /api/v1/assistant/extension-trust/{id}`, `GET` / `PUT /api/v1/assistant/conversations/{id}/categories`): a full-access client only; an extension's token or a scoped device gets 403, and agents have no tool for it. A track's own categories cannot be taken away (409); a category the user took away stays away until the user adds it back.
- A redacted push says only that there is news (`assistant-spaces.notice_*`), and a confirmation card says the content may be personal (`assistant-spaces.outbound`).
- What stays inside Persona is not a text leaving: to-do edits from a conversation (`todo_create`, `todo_update`, their repositories and workspaces) and the main chat's mirror to the owner's own Lark chat and plugin channels keep the track's rule.

## Tracks and kinds

A track is of a kind (#13472): a config whose every field picks one of the options the manager defines (`server/internal/assistant/track_kinds.go`). A new option is a code change; a new combination of options is a new kind, config only. Nothing branches on a kind's name: every decision reads a field of the track's effective config, which is its kind's with what the track sets.

- **Built-in kinds** (the manager's, never rows): `orchestration` (the main chat's way: template `assistant`, the engineering context, leaders' supervision, the assistant's memory assembly, no capture, no channels) and `space` (a domain space: template `space`, a `SPACE.md` the user writes, the track's own context and memory, no supervision, a capture target, topic and single-chat channels, listed under spaces). Both cap pushes at P0, default cards to quick, and suggest no mode on entry.
- **The user's kinds** are rows of `assistant_track_kinds`, their config a JSON object with `schema: 1`. A kind whose `schema` is newer than the manager, or whose config is not valid here, is listed as disabled (`disabled: schema` or `invalid`) and its tracks are left out (their conversations get the strictest policy) until the assistant is updated or the kind fixed. A kind asking for leaders' supervision gets the warning `supervision_leaders`: leaders review the main chat only for now.
- **Fields and options**: `template` (`assistant`, `space`), `user_instructions` (`space_md` or none), `context` (`engineering`, `track`, `none`), `default_categories` and `tag_focus` (information categories), `rhythms` (scheduled tasks a new track gets: title, five-field cron, optional IANA zone, prompt, `topic_policy` `new` or `continue`), `attention` (`push_cap` P0–P2, `deep_default` `quick` or `deep`, `enter_mode` `none` or `immersive`, never switched to on its own), `supervision` (`leaders`, `routine`, `none`), `usage`, `assembly` (`assistant`, `track`), `capture_target`, `channels` (`topics`, `single`) and `sidebar` (group, order, icon token).
- **Usage only tightens**: each `usage` rule names a scene (`source_track`, `elsewhere`, `hand_off`, `lock_screen`, `others`, `extension`, `kb_write`), a category (or `*` for all, general and unknown information included) and a rule (`allow`, `relevant`, `minimal`, `redact`, `confirm`, `deny`). A rule looser than what `usage` itself gives that category in that scene is refused (400); for `*`, it is compared with the strictest category.
- **What a track sets** (`config_override`): `tag_focus`, `rhythms` (only when the track is created; later its scheduled tasks are changed as scheduled tasks), `attention`, `usage` (added to its kind's, so it only tightens further), `capture_target` and the sidebar's `icon`. Its template and default categories are its own columns, defaulting to its kind's. Anything else in the override is refused.
- **What the settings do** (each read from the track's effective config, never its kind's name; the built-in kinds set nothing that changes behavior):
  - `rhythms`: when a track is created (`POST /api/v1/assistant/tracks`), each rhythm becomes one scheduled task of the track (`Task.space` is its slug, a cron task, on or off as the rhythm says, `created_by: track`), all in one save (`server/internal/assistant/track_rhythms.go`). `topic_policy` `new` is a new conversation each run (`fresh_each_run`), `continue` one conversation continued. A rhythm's `tz` is not kept yet: the task runs in the user's time zone, as every scheduled task does. From then on they are ordinary scheduled tasks; a later change of the kind's rhythms reaches only tracks created after it.
  - `attention.push_cap`: a push from one of the track's conversations that is no card (`notify_user`, a turn's finished push) carries at most this level; a louder one is lowered to it, and a push without a level keeps none when what the hub derives for it (P1, P2 for a finished turn) is already that quiet. Cards (questions, approvals, a to-do's decision) keep their level (`server/internal/assistant/track_attention.go`). The manager settles the level before the hub gets the push; with no track capped below P0, nothing is looked up.
  - `tag_focus`: tagging a turn of the track's conversations, or a text leaving one, asks the model to look especially for these categories and the track's default categories (`InfoTag.Focus`; a track's focus stays health).
  - `usage`: every use of the track's information (`usage`, `server/internal/assistant/usage.go`) applies the rule on top of the assistant's own and keeps the stricter. A `*` rule covers all of the track's information; a category's rule covers information carrying it, or whose categories are not known. The switches the call sites read stay on for anything stricter than their rule (`deny` on the lock screen still redacts).
  - The kind itself: every assistant process gets `PERSONA_TRACK_KIND` next to `PERSONA_SPACE`: `orchestration` in the assistant's own directory, `space` in a track's directory, a track's own kind in its directory. The manager names it on `assistant.prepare` (`track_kind`); a node from before, or a process resumed before its directory's first prepare since the node started, gives none. An Agent never takes it over from the assistant's terminal.
- **A track's own directory** (template `space`): `tracks/<slug>` in the state directory of the assistant's machine (`tracks-<id>/<slug>` for another manager), mode 0700, with `SPACE.md`, `inbox/` (what the user files into the track), `recordings/` and `.space/` (Persona's: `history/` keeps SPACE.md before Persona rewrites its state block). `SPACE.md` is written once from `server/internal/prompts/assistant/space_md.md` in the owner's language (a title, three empty sections and the state block between `<!-- persona:managed:state:begin -->` and `<!-- persona:managed:state:end -->`) and is the user's from then on. `CLAUDE.md` and `AGENTS.md` are the same file: the baseline `server/internal/prompts/assistant/space_claude_md.md` followed by the `SPACE.md` the node reads there (`assistant.prepare` with `space`, capability `track_spaces_v1`; `server/internal/node/assistant_space.go`). The node rewrites them only when they change, so editing `SPACE.md` reaches a running Claude conversation at its next message (a new process, `instructionsStale`) and a Codex conversation when the next one starts. The manager writes a new track's directory when it is created and checks every track's each minute with the assistant's instructions (`refreshInstructions`); a computer whose node does not keep track directories gets none, and a conversation of the track is not started there. Only a track in its manager's tracks directory has one (`identity.TrackDirOf`), so every process tells its conversations from the path alone (`identity.IsAssistantDir`, `identity.SpaceOf`); an archived track keeps its directory.
- **Context with each message** (#13499): a conversation in a track other than the main space gets its own short `<persona-context>` instead of the main chat's snapshot (`server/internal/assistant/space_context.go`, `server/internal/prompts/assistant/space_context.md`): the time, the track's title and the owner's language, at most 600 characters, and nothing about Agents, computers, unread Lark chats, tasks or the knowledge base. The track is told as the manager noted the conversation, else as its computer lists it (a directory inside a track counts as the track); the main conversation, leaders and the background supervisor are not looked up and keep the snapshot byte for byte. A kind whose `context` is `none` gets no context; `engineering` on a track other than the main space gets the short one for now. A track the registry does not know gets the short one, named by its slug.
- **Scheduled tasks in a track** (#13501): a task carries `space`, the track it runs in. One set up from a conversation takes that conversation's track (`schedule_routine`, `schedule_followup`); the owner may also put a task into a track, or take it out, with `space` on `POST` / `PUT /api/v1/assistant/tasks` (full credentials only, 403 otherwise; the assistant's own `""`, or a track with a directory here, 400 otherwise; a body without `space` keeps it). Moving a task leaves the conversation it came from and its own conversation behind. A task of a track never has a working directory of its own (400): it runs in the track's directory, its conversation is one of the track's (that is where its result is delivered), and what reaches the phone follows the track's policy (`server/internal/assistant/schedule_space.go`). `topic_policy` (`new` or `continue`, as a kind's `rhythms` name it) is the same choice as `fresh_each_run`: `new` starts a conversation for every run, `continue` keeps one; views carry `fresh_each_run`.
- **Reading and writing SPACE.md**: the apps read a track's `SPACE.md` with `GET /api/v1/assistant/tracks/{slug}/space-md` and the user saves it with `PUT` (`content` and the `base_digest` it was read at; a stale one is refused, so two edits never overwrite each other). The user's write may change anything but the blocks between `persona:managed` markers and the markers themselves, compared byte for byte. The track's own conversations, and only they (`spaceTools` in `server/internal/assistant/track_space_md.go`; the main chat's tool list is unchanged), get the MCP tool `space_state_update {text}`, which replaces the text of the state block alone, at most 2048 bytes; the model never edits that block itself. Both go to the node on the assistant's computer (`assistant.space_md`, capability `track_space_md_v1`, `server/internal/node/assistant_space_md.go`), which reads the file without following a link, keeps the file it replaces in `.space/history/` (the latest 20) and writes atomically. After the user's write the track's `CLAUDE.md` and `AGENTS.md` are written again at once; after the state's, at the next refresh.
- **Who changes them**: `GET` / `POST /api/v1/assistant/tracks`, `PUT /api/v1/assistant/tracks/{slug}`, `GET` / `POST /api/v1/assistant/track-kinds` and `PUT /api/v1/assistant/track-kinds/{slug}` are for full-access clients only; writes check that the caller is the user (403 otherwise), and a built-in track or kind is never changed (403). A change names the revision it was made against (409 when another came first), and a kind change that would leave one of its tracks invalid is refused (409).

## Quick capture

What the user jots down in passing (the share sheet, the watch, Siri, the web; #13502) goes into a list of its own, never into a conversation: taking one in gives the main chat no turn and no tokens. The server part is in `server/internal/assistant/captures.go`, `capture_sort.go` and `capture_brief.go`; the apps' entry points come with the clients.

- **Taking one in**: `POST /api/v1/assistant/captures` with `{client_id, source, kind, text?, url?, space_hint?}` is one insert into the manager table `assistant_captures`, answered at once (202 `{id, status}`); the target is under 300 ms at p95, so nothing else runs before the answer. `source` is `share_ios`, `share_android`, `watch`, `siri`, `web`, `feishu` or `shortcut`; `kind` is `text`, `url` or `voice` (transcribed on the device); images and files come later. `client_id` is the device's own id for the capture, sent again with every retry: the same id is one capture (200 with `duplicate: true`), so an offline watch's queue delivers it once. `space_hint` names a track the user chose; it must take captures.
- **Which tracks take captures**: a track with a directory of its own (template `space`, not archived) whose effective config has `capture_target` (the `space` kind's default; a track may turn it off).
- **Sorting** (a work loop in the manager, two at a time, woken by each new capture and every minute): one call of the model use `capture.sort` (under Sorting, `inbox.triage`, until it is given its own) sorts the capture into one of those tracks and tags its information categories. Its prompt is `server/internal/prompts/assistant/capture_sort.md`, English; the user message is JSON data: the note (its first 2,000 characters), its source, the tracks (slug, title, description) and the user's choice. The answer is a track or none, a confidence, an action (`keep`, `discuss`, `research`), a title and the categories. A capture the user put in a track is only tagged. Its categories are the model's and the track's default categories, kept as `assistant_info_categories` rows of kind `capture`; with none, a row that says it was tagged with none. With no model set up, captures stay `new`, listed; a call that fails is tried again, up to five times, then the capture is `failed`, still listed.
- **Filing**: only filing happens without the user, and only when the user chose the track or the confidence is at least 0.8. The node of the assistant's machine writes `inbox/<date>-<id>.md` in the track's directory (a short front matter with the id, time, source, kind and categories, the title, then what was captured), through `assistant.track_inbox_write` (capability `track_inbox_v1`, `server/internal/node/track_inbox.go`): the directory must be that track's own and a real folder, `inbox/` a real folder in it, the name a plain file name, and the file is written new and renamed into place, never through a link. While that computer is offline or its node cannot, the capture waits, `sorted`, and is filed once it can, without asking the model again. The others stay `sorted` for the user ("discuss" and "research" only ever run when the user picks them).
- **What the owner is told**: a filed capture is pushed quietly (P2): its title and track, or, when it carries a sensitive category or was not tagged, only "1 capture" (`assistant-captures.count`), no title, track or content. The morning and evening briefings (routines with facts) get a quick-capture section on the card and in the model's facts: how many wait to be sorted, those filed since the window began by title and track (five at most), and the sensitive ones only counted ("1 capture").
- **The list**: `GET /api/v1/assistant/captures[?status=]` (the newest 200) is the user's own view, scene 1: every capture with its text, sort, where it was filed and its categories. Both routes are for full-access clients only (403 otherwise).

## API

For the exact protocol, see the "Assistant" table in `docs/protocol/protocol.md`.

| Endpoint | How a track's space uses it |
| --- | --- |
| `POST /api/v1/assistant/conversations` | With `"space":"<slug>"`, starts a new chat in the track's directory (writing its CLAUDE.md first). Combined with `"main":true` it returns 400 (a space has no main chat); an unknown `space` returns 400 |
| `GET /api/v1/assistant?space=<slug>` | Lists the space's chats; `cwd` is the track's directory. Without `space` it lists only the assistant's own chats. `?archived=1` works the same; an unknown `space` returns 400 |
| `GET /api/v1/assistant/memory?space=<slug>` | The space's memory `{"files":[…],"dir"}` |
| `PUT / DELETE /api/v1/assistant/memory/{name}?space=<slug>` | Edit or delete one memory in the space |
| `sessions` push, session list | A track's chats carry `space: "<slug>"` |

Once a chat is open it behaves like any other assistant chat: sending, archiving, renaming and compacting all use the existing endpoints (`/api/v1/assistant/conversations/{id}/…`, `/api/v1/sessions/{mid}/{sid}/…`) without `space`.

## Tool isolation

The `conversation*` tools in a chat only see chats in the same space (`server/internal/assistant/conversations.go`: `spaceConversation`, `ownSpaceConversation`, `selfSpace`):

- `conversations_list`: in a track's chat it lists only that space's chats; in an assistant chat only assistant chats.
- `conversation_read`, `conversation_rename`, `conversation_archive`, `conversation_send`: a target in another space is treated as not found.
- `conversation_new`: a new chat started from a track's chat stays in the track.
- Calls not made from a chat (no caller session id) count as the assistant's own space.
- `kb_update` from a space whose policy says so (`NoKBWrite`) fails outright: what is said there does not go into the knowledge base (`assistant/tools.go` `runTool`). Knowledge base reads (`kb_search` etc.) work as usual.
- Scheduled follow-ups and scheduled tasks created in a track's chat (`schedule_followup`, `schedule_routine`) record their space (`Task.space`); when one fires and needs a new chat, it opens in that track. The space owns the task's working directory: a nonempty task `cwd` is rejected when saving and before dispatch, including an older stored override. Clear it to restore the canonical directory. Launcher, model, effort and execution computer remain configurable under their existing validation; the selected computer prepares the track's instructions and directory. A follow-up continues its source chat only when its actual directory matches the freshly prepared directory, with the node enforcing that directory on resume. Missing or mismatched source context uses the existing safe replacement path. Normal-space tasks keep their custom directories.
- When the calling chat's space cannot be determined (the assistant's machine cannot list it for the moment), it is treated as the main space: it can only reach main-space chats, and a track's chats can never be listed or read. The worst case is a track's chat temporarily seeing the main space's list; a space's content is never exposed elsewhere the other way round.
- `list_followups` lists only this space's scheduled tasks; editing with `schedule_routine` and an id, or deleting with `delete_routine` / `cancel_followup`, treats tasks in another space as not found.
- Extensions' skills and gated commands reach every space (there is no per-space contribution). Every assistant process carries its space in `PERSONA_SPACE` (`<slug>` / `main`, #6003, `docs/extensions/extensions.md` "Assistant"), so a command meant for one space alone can refuse elsewhere; a `cd` into the track's directory does not change it. Its track's kind is in `PERSONA_TRACK_KIND` ("Tracks and kinds").
- All other tools (phone tools, reminders, mail, Lark, Agents…) exist in every space: information can be sent to whoever the user wants; the rules are under "Outbound" below.

## Outbound (#3194)

The boundary is not "sensitive information may not leave" but "it may not leave without the user knowing". Emailing results to a doctor, or sending them over Lark to a coach or family, is legitimate and still works. In a space the decision always depends on the chat's space (the trusted session directory), never on a model judging "does this sentence count as sensitive": a track with a sensitive default category makes every exit below strict without asking a model. Outside a track the same exits judge the words leaving ("Using information by scene").

| Exit | In a sensitive track's chat | Code |
| --- | --- | --- |
| Push: turn ended, `notify_user`, plan waiting for you to start, scheduled task failed | Only says there is news ("There is something new. Open Persona to see it."), without the body, chat title or task name | `hub/machine.go` `doneAlert`, `assistant/tools.go`, `tasks.go`, `schedule.go` |
| Phone local notification: `phone_notify` | The manager replaces the title and body with the same localized notice as `notify_user` before forwarding to the phone | `assistant/fleet_tools.go` `mcpCall`, `assistant/space.go` `redactedNotice` |
| Push for question / authorization cards | The lock screen likewise only says there is news; the card content is viewed in the App. A card is judged by its chat's directory: the node and then the manager place a card of an assistant chat in the chat's directory, not the hook's after a `cd` (`identity.CardCwd`, the manager's `placeCard` covers older nodes), and any directory inside a track counts (`identity.SpaceAt`, #2368) | `hub/push_payload.go` `interactionPayloadIn` (looks at `ix.Cwd`), `assistant/fleet_machines.go` `placeCard` |
| Lark bot, plugin channels | Forwarded `notify_user` only says there is a new message; to-do reminders keep the generic notice without a specific to-do URL or ID in the card or a to-do reply binding (ordinary reminders retain their detail button, notes and reply context); answers in a scheduled task's chat are not mirrored; "all cards" and "all questions" exclude the track's chat cards (the chat the channel itself is driving works as usual) | `assistant/feishu_cards.go`, `feishu_push.go`, `channels_plugin.go` |
| `agent_send` / `agent_start` | Confirmed on the phone every time. `agent_send` accepts targets in the conversation's own space. The card explains that the Agent keeps its copy after the chat is deleted | `assistant/space.go` `confirmOutbound` |
| `task_plan` | Never starts automatically; always waits for the user to tap start on the plan card | `assistant/tasks.go` |
| `mail_send` and connector write operations | Confirmed on the phone every time; gate allow rules do not let it through (deny still rejects) | `connector.ConfirmEach`, `callConnector` in `extmgr/connectors.go` |
| Lark write operations (lark-cli, command gate) | Confirmed on the phone every time; allow rules do not let it through, and there is no **Always Allow in Session**; reads work as usual (deny still rejects). Both entrances hold it: the gated command (`larkCheck`) and the node's gate proxy, which a script can call without the command: a track process's proxy address lets a write through only with the one-time grant `larkCheck` leaves once the phone confirmed it. Both decide the space from a record made when the conversation's process is started, not from the directory a command runs in (a `cd` moves it); a hook directory that is itself in a track counts too, so a mix-up can only ask more | `node/larkgate.go` `larkCheck`, `node/gateproxy.go` `ServeHTTP` |

Explicit reminders created with `phone_reminders_create` keep the user-requested text and require confirmation on the phone. Memory and chats within the same space need no confirmation.

Known limit: a gate proxy address does not know who calls it. A process in a track's conversation could in principle learn the address of another conversation (another process of the same user has an environment that can be read), the same kind of gap as the Bash one under "How directories and memory are isolated": closing it needs the sandbox or OS-level isolation (see "Later").
